clangd vs clice

I wrote this article to give a fair comparison of clangd and clice. The clice 1.0 announcement reached a sweeping conclusion that I think goes further than the evidence supports.

The measurements come from the macOS test environment on my personal laptop. I’m writing in my personal capacity. The views here are mine alone.

The picture is more mixed. Setup depends on the editor and toolchain, the two servers support different workflows, and performance depends on what you measure. I look at all three, alongside project maintenance.

Cold background indexing

Time, memory, and disk

clangd + clang-tidy · 723 translation units

These runs measure first-time background indexing. Editor response latency, incremental changes, and reopening a project with a warm cache call for separate measurements.

Each memory sample sums resident memory across the server and every descendant. The average and peak come from those process-tree totals. Each memory bar is the median of the corresponding per-run statistic.

Inspect individual runs

clice can keep multiple variants of a header and records each translation unit’s include tree. Additional analysis and a richer index can make a longer first pass worthwhile. Storage format and implementation choices can also affect the time and size, so the benchmark leaves the cause of the gap open.

clangd still finished background indexing sooner on this workload. That is a concrete counterexample to the release article’s broad claim that clice surpasses clangd in performance.

clice index designWhat clice records

I saw the same pattern on Linux. In my own testing there, clice took substantially longer to finish background indexing than clangd. That Linux test was informal. The timed measurements above come from macOS.

Where a warm cache could favor clice

Reopening a project. clangd loads cached background-index shards and merges them into an in-memory index. clice opens its persisted LMDB index and reads records on demand. That can reduce the work clice has to do up front when reopening a large project.

Opening an indexed file. With default settings, clangd builds a preamble when it opens a file even if the project index is already available. Closing the file drops its document worker, so reopening it normally builds the preamble again. clice can answer some requests, such as navigation, directly from an up-to-date background index while the document compile is pending. Its default mode still compiles the document when needed. The readonly rules can serve browsing from the index without building an editor preamble.

Reusing a preamble. clice's background index and editor preamble cache have separate roles. A file that was only background-indexed can still need its first editor preamble. When a compatible preamble is already cached, clice can reuse it after a close or a server restart, which may make an include-heavy file quicker to reopen.

These are plausible warm-cache advantages. The timings above measure cold indexing.

Editor workflows

Where the tools differ

Both cover completion, diagnostics, navigation, references, rename, formatting and semantic highlighting. The differences show up in specific workflows. This comparison uses clice’s tagged 1.0 documentation and clangd’s published docs and release source.

Ease of use

Both servers can discover a CMake-generated compile_commands.json. clice’s automatic probing can simplify setup for toolchains such as nvcc or zig cc, where clangd may need driver or include-path configuration. The editor can change the picture. clice’s VS Code extension bundles the server, while Zed already ships clangd as its built-in C and C++ server and requires configuration to switch to clice.

Where the fast-check list comes from

clice 1.0 ships a byte-for-byte copy of clangd 23.1.0’s generated cost table. clangd generates it by timing individual checks on Clang’s Sema.cpp. clice uses the table at runtime to filter the checks selected by .clang-tidy. The shared entry for misc-const-correctness marks it slow and records a 103% increase in parsing time, about twice the baseline for that file. Both editors skip it by default even when the project enables it.

Project continuity

Who maintains each server?

clangd

LLVM lists two active clangd maintainers, Nathan Ridge and Aleksandr Platonov. Contributors continue to review patches by hand. Over the three months ending November 18, 2026, 61 commits touched clang-tools-extra/clangd on LLVM’s main branch.

clice

Over the same period, 386 commits landed in the clice repository. At the 1.0 tag, 892 of 1,000 reachable commits list ykiko as author. Other contributors are visible in the history. In the release article, ykiko says maintenance will continue at a lower intensity, with incremental optimizations and bug fixes driven by user feedback. The concentration of past work makes succession worth watching.

Reproducibility

How the benchmark ran

Workload
723 existing translation units from the LLVM CMake compilation database at bd49d77ae3c0. The workload includes 245 units under clang-tools-extra/clangd and 478 under clang-tools-extra/clang-tidy. One stale database entry referred to a file absent from the checkout.
Host and binaries
macOS 27.2.1 on arm64, eight logical CPUs and 8 GiB RAM. I used the official macOS binaries of clangd 23.1.0 and clice 1.0.0. The release article uses the same clangd version in its examples. Both received the same CMake commands with staged paths and the macOS 27.2 SDK. The commands kept the textual forced includes and dropped binary PCH inputs produced by the local compiler. clangd release · clice release
Timing
Wall time from sending the initialized and open-file messages to the last background-index progress-end event. The harness follows clice’s additional passes when its logs show queued retries. I ran one server at a time in a regular macOS Terminal, with a fresh index cache for every run. The order was clangd, clice, clice, clangd, clangd, clice. OS file caches were left in their normal state.
Worker settings
clangd ran with -j=4 and normal background indexing priority. clice used background = 4, max = 4, foreground = 1, and background_delay_ms = 0 under [workers]. Both had a background concurrency ceiling of four. clice can reduce concurrency under memory pressure.
Memory
macOS proc_pid_rusage was sampled about every 200 ms. Each row sums the resident set size of the server and all descendants. The mean averages those samples, and the peak is the largest sampled sum. Summed RSS can count shared pages in more than one process and can miss peaks between samples. Raw samples also include physical footprint.
Index size
Logical bytes of the persisted symbol index after clean shutdown. The total covers clangd’s *.idx shards or clice’s index.mdb database. Locks, logs, PCH and PCM caches are outside this total. Filesystem-allocated bytes are also in the raw data. The formats and indexed coverage can differ.
Completion
Translation-unit counts come from the server logs. A progress end event can also occur after skipped work. The results include coverage so a shorter or lower-memory incomplete run cannot be mistaken for an equivalent completed index. The two indexes record different information. Coverage here counts translation units in the logs.

My take

clice is a worthwhile project with ideas I’d like to see more language servers explore. Process isolation addresses a real reliability problem. Its work on named modules and non-self-contained headers makes a concrete difference for projects that use them.

Those strengths make clice an innovative alternative. Calling it a successor that surpasses clangd across the board would take much broader evidence. The label “next-generation” is too vague to settle which tool fits a given codebase. The workflows you use, the resources your machine has, and the support you can count on matter more.
