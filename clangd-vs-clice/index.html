clangd vs clice

I tried clice after the 1.0 release. One line in the announcement made me want to compare it directly with clangd.

I ran the benchmark on my personal Mac. The opinions here are my own.

I think that claim is too broad. I wanted to compare the two fairly, so I looked at how each fits into an editor workflow and timed them indexing the same code. I also went through their recent commit history and looked at who’s maintaining each project.

Inspect individual runs

clice keeps multiple variants of a header and records each translation unit’s include tree. If you need that information, a longer first index can be a fair trade. The storage format and the way each server builds its index can also affect the time and disk space.

For this workload, though, clangd finished the first index sooner. That’s one concrete case where the release article’s performance claim breaks down.

clice index designWhat clice records

I saw clice take substantially longer to index on Linux, too. That was an informal test. The figures above come from the macOS runs.

Where a warm cache could favor clice

Reopening a project. clangd loads cached background-index shards and merges them into an in-memory index. clice opens its persisted LMDB index and reads records on demand. On a large project, that can mean less work up front for clice.

Opening an indexed file. With default settings, clangd builds a preamble when it opens a file even if the project index is already available. Closing the file drops its document worker. When you reopen the file, clangd usually builds the preamble again. clice can answer some requests, such as navigation, directly from an up-to-date background index while the document compile is pending. Its default mode still compiles the document when needed. The readonly rules can serve browsing from the index without building an editor preamble.

Reusing a preamble. A file can be in clice’s background index and still need a preamble the first time you open it. Once clice has cached that preamble, it can reuse it after you close the file or restart the server, as long as the preamble is still valid. That could save time on a file with a lot of includes.

I’d expect clice to do better in some of these cases. The benchmark above only times the first index.

Editor workflows

Where the tools differ

Both servers cover the basics, including completion, diagnostics, navigation, rename, and formatting. Here are the differences that stood out in the release docs and source.

Ease of use

Both servers can discover a CMake-generated compile_commands.json. clice’s automatic probing can simplify setup for toolchains such as nvcc or zig cc, where clangd may need driver or include-path configuration. The editor matters, too. The clice extension for VS Code bundles the server. In Zed, clangd comes built in for C and C++ and switching to clice takes some configuration.

Where the fast-check list comes from

clice 1.0 ships a byte-for-byte copy of clangd 23.1.0’s generated cost table. clangd generates it by timing individual checks on Clang’s Sema.cpp. clice uses the table at runtime to filter the checks selected by .clang-tidy. The shared entry for misc-const-correctness marks it slow and records a 103% increase in parsing time, about twice the baseline for that file. Both editors skip it by default even when the project enables it.

Reproducibility

How the benchmark ran

Workload
723 existing translation units from the LLVM CMake compilation database at bd49d77ae3c0. The workload includes 245 units under clang-tools-extra/clangd and 478 under clang-tools-extra/clang-tidy. One stale database entry referred to a file absent from the checkout.
Host and binaries
macOS 27.2.1 on arm64, eight logical CPUs and 8 GiB RAM. I used the official macOS binaries of clangd 23.1.0 and clice 1.0.0. The release article uses the same clangd version in its examples. Both received the same CMake commands with staged paths and the macOS 27.2 SDK. The commands kept the textual forced includes and dropped binary PCH inputs produced by the local compiler. clangd release · clice release
Timing
The timer starts when the harness sends the initialized and open-file messages. It stops at the last background-index progress-end event, including any extra clice passes for queued retries. I ran one server at a time in macOS Terminal with a fresh index cache for every run. The order was clangd, clice, clice, clangd, clangd, clice. I left macOS to manage its file caches normally.
Worker settings
clangd ran with -j=4 and normal background indexing priority. clice used background = 4, max = 4, foreground = 1, and background_delay_ms = 0 under [workers]. Both had a background concurrency ceiling of four. clice can reduce concurrency under memory pressure.
Memory
The harness uses proc_pid_rusage to sample the process tree about every 200 ms. It computes the average and peak from the sum of each sample. Summing RSS can count a shared page more than once, and a short spike can fall between samples. The raw data also includes physical footprint.
Index size
Logical bytes of the persisted symbol index after clean shutdown. The total covers clangd’s *.idx shards or clice’s index.mdb database. Locks, logs, PCH and PCM caches are outside this total. Filesystem-allocated bytes are also in the raw data. The formats and indexed coverage can differ.
Completion
A server can report that indexing ended even when it skipped some work. I checked the logs for the number of translation units each run actually indexed. All six runs covered the full set.

My take

I’m glad clice exists. A compiler crash taking down the whole language server is a real problem, and isolating compiler work in separate processes is an idea I’d like to see more servers try. clice also does things I’d want if I were working heavily with C++20 modules or headers that need their includer.

I’d call clice a promising alternative. The “next-generation” label tells me very little about which tool will work better for a particular codebase. For this LLVM checkout, I’d take clangd’s shorter wait for a first index. For a project built around modules, I’d give clice’s editor support a closer look.
